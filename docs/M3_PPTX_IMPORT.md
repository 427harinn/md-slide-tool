# M3: PPTX -> QMD Import

## Purpose

M3 adds a manual import path from a PowerPoint file generated by md-slide-tool back into its paired QMD and assets file.

M3 is not a general-purpose arbitrary PPTX -> Markdown converter. Its supported source is a PPTX produced by md-slide-tool and then edited in Microsoft PowerPoint.

Initial CLI:

```bash
slidegen import presentation.pptx
```

The corresponding `presentation.qmd` must already exist. Existing QMD front matter is preserved; the slide body is rebuilt from the saved PPTX.

M3 intentionally remains manual. File watchers, automatic synchronization, dirty-state handling, and conflicts belong to M4/M5.

## Core direction

### 1. Source of truth during import

During `slidegen import`, the saved PPTX is the source of truth for supported slide content and supported visual layout.

Examples:

- PowerPoint slide reorder -> QMD slide order changes.
- PowerPoint slide deletion -> corresponding QMD slide is removed.
- PowerPoint title/body edits -> normalized QMD content changes.
- PowerPoint image move/resize/crop -> assets layout changes.

M3 does not perform a fine-grained bidirectional merge between QMD and PPTX.

### 2. Preserve QMD front matter

The existing QMD YAML front matter is preserved.

M3 v1 rebuilds the normal slide section under the front matter from the PPTX. It does not try to infer Quarto configuration, reference-doc settings, or other project configuration from PowerPoint.

The first title slide produced from front matter remains front-matter-managed in M3 v1. Editing that title slide directly in PowerPoint is not imported back yet.

### 3. Stable slide identity

For managed slides, `slide-id` stored in PPTX slide metadata is the primary identity.

Existing identified slides keep the same `slide-id`.

If PowerPoint contains a newly added supported slide without an md-slide-tool `slide-id`:

1. generate a new `slide-id`;
2. use it in the rebuilt QMD;
3. write it back into the PPTX before committing the import.

Do not infer identity from title text or slide position when a stable ID exists.

### 4. Supported text reconstruction

M3 v1 supports normalized reconstruction of:

- slide title;
- ordinary paragraphs;
- bullet lists;
- numbered lists.

The goal is not byte-for-byte recovery of the original Markdown syntax. PowerPoint does not retain all original Markdown semantics.

M3 writes normalized Markdown representing the supported semantic structure.

M3 v1 does not promise faithful roundtrip for:

- arbitrary inline formatting;
- original Markdown whitespace;
- callouts;
- code blocks;
- tables;
- equations;
- SmartArt;
- charts;
- arbitrary free-position text boxes;
- unsupported native PowerPoint structures.

### 5. Supported image identity

Images use the existing general `element-id` model.

For an existing picture carrying an md-slide-tool `element-id`, import preserves the same logical element.

If PowerPoint changes the image contents while preserving the identified picture shape, the image remains the same element and keeps the same `element-id`.

If the old shape is deleted and a new picture shape is inserted, the new picture has no stable ID. M3 treats it as a new element and generates a new `element-id`. It must not guess replacement based on position or visual similarity.

### 6. New PowerPoint images

For a new supported picture without `element-id`:

1. generate a new `element-id`;
2. extract the image;
3. add normalized QMD image syntax with that `element-id`;
4. add its layout to assets;
5. write the new `element-id` back to the PowerPoint picture shape.

### 7. Extracted/replaced image storage

Do not overwrite a shared existing source image just because one PowerPoint picture was replaced.

When PowerPoint contains image content that differs from the source represented by the current QMD path, extract it under:

```text
img/imported/<element-id>.<ext>
```

This allows separate slides/elements that previously referenced the same source image to diverge safely.

If the picture content is unchanged and the existing path remains valid, keep the existing source path where practical.

### 8. Image move and resize

For every supported image element, import reads PowerPoint shape geometry and writes:

- x
- y
- width
- height

to `<stem>.assets.json` as EMU integers.

The next QMD -> PPTX render must reproduce the imported rectangle.

### 9. Image crop

PowerPoint image crop is a supported M3 feature because it is a common editing operation.

The original image file should not be destructively cropped.

Persist crop as per-element layout metadata in assets, conceptually:

```json
{
  "elementId": "element-...",
  "type": "image",
  "x": 1000000,
  "y": 1000000,
  "width": 3000000,
  "height": 2000000,
  "crop": {
    "left": 0.10,
    "top": 0.05,
    "right": 0.15,
    "bottom": 0.00
  }
}
```

Implementation may use the exact numeric representation exposed by python-pptx/Open XML if that preserves PowerPoint semantics more accurately, but it must:

- roundtrip without materially changing the visible crop;
- remain per-element;
- remain backward compatible with existing assets that have no crop field;
- avoid modifying the original source image solely to represent crop.

Crop support is part of the M3 design. Rotation and z-order remain out of scope.

### 10. Image deletion

If an identified image is absent from a successfully parsed supported PowerPoint slide, remove that image from rebuilt QMD and assets.

Do not perform destructive cleanup until the complete import has passed validation.

### 11. Slide reorder and deletion

PPTX slide order becomes normal-slide order in rebuilt QMD.

A previously managed slide that is no longer in the PPTX is removed from the rebuilt slide body.

The front-matter-generated title slide remains outside normal stable-slide reconstruction in M3 v1.

### 12. Unsupported content is not silently discarded

An import must not report success if the subsequent QMD -> PPTX render would silently erase unsupported user-created PowerPoint content.

Examples include unsupported shapes, SmartArt, charts, unsupported text structures, rotation, or other native content not represented by the M3 model.

Default policy:

- unsupported content with a meaningful risk of data loss -> FAIL import before commit;
- harmless/template-only structures that can be positively identified as non-user content may be ignored;
- do not classify unknown content as harmless by guesswork.

The implementation must define explicit classification rules and tests.

### 13. Managed PPTX only

M3 v1 requires an existing same-stem QMD and evidence that the PPTX is part of the md-slide-tool workflow.

Stable IDs may be absent from newly created PowerPoint slides/images, but the presentation as a whole must be a managed presentation.

A completely unrelated arbitrary PPTX with no managed identity/context must be rejected rather than converted heuristically.

### 14. Template versus user content

The importer must distinguish supported user content from known template/master/layout artifacts.

Do not import decorative template objects into QMD as user content.

Do not rely solely on visual position to decide whether an object is template content.

### 15. Atomic import

Import must not leave partially updated files.

High-level flow:

```text
read PPTX + existing QMD/assets
-> parse
-> validate all supported/unsupported content
-> allocate any missing IDs
-> stage rebuilt QMD
-> stage assets
-> stage extracted images
-> stage PPTX metadata updates if IDs were allocated
-> commit only after all required stages succeed
```

If import fails, the original QMD, assets, managed image files, and PPTX must remain usable and unchanged.

### 16. Text is not persisted in intermediate JSON

Continue the existing design principle:

- QMD is the persisted textual representation.
- assets stores visual element layout/state.
- do not create a persistent intermediate JSON copy of slide title/body text.

Temporary in-memory or temporary-file structures used during import are allowed but must not become a second canonical document store.

## CLI behavior

Initial supported form:

```bash
slidegen import presentation.pptx
```

Expected paired files:

```text
presentation.pptx
presentation.qmd
presentation.assets.json
img/
```

Do not add `--watch`, `--sync`, automatic save monitoring, or conflict merge behavior in M3.

## M3 scope

M3 includes:

- manual `slidegen import`;
- managed PPTX validation;
- existing stable slide/element identity;
- new stable IDs for newly added supported PowerPoint slides/images;
- writing new IDs back to PPTX;
- slide title import;
- ordinary paragraph import;
- bullet/numbered-list import;
- slide reorder/delete;
- image add/delete/replace;
- image extraction under `img/imported/`;
- image x/y/width/height import;
- image crop import and render roundtrip;
- assets update;
- front matter preservation;
- atomic commit behavior;
- explicit unsupported-content detection.

## Out of scope

- arbitrary external PPTX conversion;
- automatic watcher/sync;
- dirty-state conflict detection;
- automatic text merge;
- PowerPoint Add-in;
- arbitrary shapes;
- lines/arrows;
- SmartArt;
- charts;
- arbitrary free-position text boxes;
- tables/equations unless separately approved before implementation;
- rotation;
- z-order;
- Marketplace publication;
- PPTX -> Word;
- importing PowerPoint edits to the front-matter-managed title slide.

## Future considerations

These are intentionally not M3 requirements but must remain tracked:

- hide/internalize `slide-id` / `element-id` so normal users do not need to see implementation metadata;
- incremental/selective build to avoid expensive full rebuilds;
- explicit build state UI;
- prevent or safely queue edits/build requests while a build is running;
- M4 watcher/debounce/running/pending/self-generated-write suppression;
- M5 dirty-state conflict handling;
- shape/line/arrow support using the existing general `element-id` identity model.
