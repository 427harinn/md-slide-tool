# M3: PPTX -> QMD Import

## Purpose

M3 adds a manual import path from a PowerPoint file generated by md-slide-tool back into its paired QMD and assets file.

M3 is not a general-purpose arbitrary PPTX -> Markdown converter. Its supported source is a PPTX produced by an M3-capable md-slide-tool render and then edited in Microsoft PowerPoint.

Initial CLI:

```bash
slidegen import presentation.pptx
```

The corresponding `presentation.qmd` must already exist. Existing QMD front matter is preserved; the normal slide body is rebuilt from the saved PPTX.

M3 intentionally remains manual. File watchers, automatic synchronization, dirty-state merge/conflict UI, and background build coordination belong to M4/M5.

## 1. Presentation-level managed marker

M3 must not guess whether a PPTX belongs to md-slide-tool.

An M3-capable render writes presentation-level metadata into the PPTX package using Office/Open XML custom document properties (or an equivalent package-level property mechanism that survives desktop PowerPoint save):

- `md-slide-tool.managed = 1`
- `md-slide-tool.format-version = 1`
- `md-slide-tool.document-id = document-<uuid>`
- `md-slide-tool.qmd-body-sha256 = <sha256>`

The exact package representation may be implemented in `docProps/custom.xml` or an equivalent standards-compatible property part, but the property names and semantics above are the logical contract.

A PPTX is accepted by M3 only when:

1. the same-stem QMD exists;
2. the same-stem assets file is readable as schema v1 or v2;
3. the managed marker exists and is valid;
4. the PPTX document-id is valid;
5. the paired assets schema v2 documentId equals the PPTX document-id;
6. stable slide/element IDs that are present are syntactically valid and non-duplicated;
7. the current QMD normal-slide body hash matches the render baseline described below.

### PPTX/QMD pairing contract

M3 does not pair a PPTX with a QMD by stem name or body hash alone.

Assets schema v2 adds a top-level document identity:

```json
{
  "schemaVersion": 2,
  "documentId": "document-<uuid>",
  "slideSize": { "...": "..." },
  "elements": []
}
```

An M3-capable render establishes or reuses one document-id and writes the same value to:

- PPTX presentation-level `md-slide-tool.document-id`;
- same-stem `assets.json.documentId`.

Import requires exact equality. A same-body QMD paired with a different managed PPTX therefore fails with a document-pair mismatch instead of passing only because the text hash happens to match.

For legacy assets schema v1, the first M3-capable render generates a document-id, upgrades assets to schema v2, and writes that document-id into both assets and PPTX. `slidegen import` never upgrades an unpaired v1 presentation heuristically.

A PPTX produced before M3 and lacking the presentation-level marker is **not imported heuristically**. The user must render it once with an M3-capable version first. This deliberately avoids ambiguous legacy classification.

Because the presentation marker exists independently of slide IDs, a managed presentation remains identifiable even if all previously managed normal slides were deleted in PowerPoint.

Invalid or missing presentation metadata causes a pre-commit FAIL.

## 2. QMD render baseline and unrendered-edit protection

Importing a PPTX rebuilds the QMD normal-slide body. Therefore M3 must prevent accidental loss of QMD edits made after the PPTX was rendered.

During every M3-capable QMD -> PPTX render:

1. stable IDs are normalized/added first;
2. compute SHA-256 over the canonical QMD normal-slide body defined below;
3. store that hash as `md-slide-tool.qmd-body-sha256` in the PPTX.

### Canonical body-hash bytes

The hash algorithm is deterministic and shared by render/import:

1. read the QMD as UTF-8; a leading UTF-8 BOM is accepted and removed for hashing;
2. identify YAML front matter only when the document begins (after optional BOM) with a delimiter line exactly `---` followed by LF or CRLF;
3. the closing delimiter is the next delimiter line exactly `---`; the normal-slide body starts immediately after that delimiter's line ending;
4. if no valid front matter exists, the normal-slide body begins at the first document byte;
5. normalize CRLF and bare CR line endings in the body to LF;
6. do **not** Unicode-normalize, trim whitespace, collapse blank lines, or add/remove a trailing newline;
7. encode the normalized body as UTF-8 and hash those bytes with SHA-256.

Front matter bytes are preserved separately and excluded from the body hash.

Tests must cover UTF-8 BOM, LF, CRLF, bare CR, no-front-matter documents, empty body, trailing newline/no trailing newline, and whitespace-only body changes.

Before `slidegen import` changes any file:

1. read the current same-stem QMD;
2. preserve front matter separately;
3. compute the current normal-slide body SHA-256 using the same algorithm;
4. compare it with the PPTX baseline.

If the hashes differ, import FAILS before staging/commit with an explicit `QMD_CHANGED_SINCE_RENDER` style error.

M3 does not add a force-merge path. The user must intentionally reconcile or re-render first. Full dirty-state conflict UX belongs to M5.

After a successful import, update the PPTX baseline hash to the newly committed canonical QMD body hash.

## 3. Source of truth during import

After the managed-marker and QMD-baseline preflight passes, the saved PPTX is the source of truth for supported normal-slide content and supported visual layout.

Examples:

- PowerPoint slide reorder -> QMD slide order changes.
- PowerPoint slide deletion -> corresponding QMD slide is removed.
- PowerPoint title/body edits -> normalized QMD content changes.
- PowerPoint image move/resize/crop -> assets layout changes.

M3 does not perform a fine-grained bidirectional text merge.

## 4. Front matter and title-slide role

The existing QMD YAML front matter is preserved exactly.

The front-matter-generated title slide is not imported back into front matter in M3 v1, but it must be distinguished reliably from newly inserted PowerPoint slides.

An M3-capable render assigns the generated title slide a reserved internal slide role marker that survives PowerPoint save. The intended representation is the slide name:

```text
mdst-title-<document-uuid>
```

Normal managed slides continue to use `slide-<uuid>`.

Rules:

- Title-slide identification uses the reserved role marker, not position.
- Moving the title slide does not change its role; it remains excluded from normal-slide QMD reconstruction.
- Deleting the title slide is allowed; front matter remains unchanged.
- More than one title-role marker is invalid and causes FAIL.
- A marker-enabled managed presentation containing an ID-less slide that uses the title-slide layout is ambiguous; M3 FAILS rather than guessing whether it is a lost title marker or a newly inserted title-style slide.
- New supported normal slides must use supported normal layouts/placeholders; they receive a new `slide-id`.
- Loss/corruption of the reserved title marker is treated as unsupported metadata tampering when classification becomes ambiguous.

Fixtures must cover title-slide move, deletion, duplicate marker, marker loss/ambiguity, and new normal slides inserted before/after the title slide.

## 5. Stable slide identity

For managed normal slides, `slide-id` stored in PPTX slide metadata is the primary identity.

Existing identified slides keep the same `slide-id`.

If PowerPoint contains a newly added supported normal slide without an md-slide-tool `slide-id`:

1. verify it is not the reserved title slide and does not use an ambiguous title-slide layout;
2. generate a new `slide-id`;
3. use it in the rebuilt QMD;
4. write it back into the staged PPTX before commit.

Do not infer identity from title text or slide position when a stable ID exists.

Any malformed stable ID or duplicate `slide-id` causes FAIL. Do not silently repair duplicates.

## 6. Supported text reconstruction

M3 v1 supports normalized reconstruction of:

- slide title;
- ordinary paragraphs;
- bullet lists;
- numbered lists.

The goal is not byte-for-byte recovery of the original Markdown syntax. PowerPoint does not retain all original Markdown semantics.

M3 writes normalized Markdown representing the supported semantic structure.

M3 v1 does not promise faithful roundtrip for:

- arbitrary inline formatting;
- original Markdown whitespace;
- callouts;
- code blocks;
- tables;
- equations;
- SmartArt;
- charts;
- arbitrary free-position text boxes;
- unsupported native PowerPoint structures.

## 7. Template/layout content classification

Template and user content must be separated by explicit structural rules, not visual position.

Initial classification contract:

- Objects inherited only from slide master/layout are not imported as user content.
- Supported title placeholders (for example title/center-title placeholder roles) are interpreted as slide title only on supported normal slides.
- Supported body/content placeholders are interpreted as paragraph/list content only when their paragraph structure is within the M3 supported subset.
- Picture shapes are supported image elements as described below.
- md-slide-tool-generated image caption textboxes are supported internal companion objects and are classified by a reserved deterministic marker, not by position/text appearance.
- All other slide-local autoshapes, arbitrary text boxes, groups, tables, charts, SmartArt/diagram content, OLE/media, and other unclassified slide-local objects are unsupported and cause pre-commit FAIL unless a future design explicitly adds support.
- Unknown slide-local content is never ignored because it looks decorative.

### Caption companion contract

The current renderer creates image captions as slide-local textboxes. M3 must make those boxes distinguishable from arbitrary user textboxes.

An M3-capable render names each generated caption textbox:

```text
mdst-caption-<element-uuid>
```

where the suffix is the associated picture's stable `element-id` without inventing a second identity system.

Rules:

- at most one caption companion may exist for a given picture element;
- a caption companion without a matching picture element is invalid and causes FAIL;
- duplicate caption companions for one element cause FAIL;
- caption text is imported as the Markdown image alt/caption text for that image;
- moving or styling the caption textbox does not create an independently persisted layout element in M3;
- a user-created arbitrary textbox that lacks the reserved marker remains unsupported;
- legacy M2-generated caption textboxes have no marker, so an M3-capable render must regenerate/upgrade the PPTX before M3 import is allowed.

Before implementation proceeds past the feasibility task, fixtures must enumerate the actual `slide.shapes` produced by the repository's supported PPTX templates, including slides with captions, and verify that inherited master/layout decoration is absent from the slide-local import model or explicitly classifiable. If a supported current template generates additional slide-local decorative objects, the design must add a deterministic marker/structural rule for them before implementation continues. Position/color/name heuristics alone are not acceptable.

## 8. Supported image identity

Images use the existing general `element-id` model.

For an existing picture carrying an md-slide-tool `element-id`, import preserves the same logical element.

If PowerPoint changes the image contents while preserving the identified picture shape, the image remains the same element and keeps the same `element-id`.

If the old shape is deleted and a new picture shape is inserted, the new picture has no stable ID. M3 treats it as a new element and generates a new `element-id`. It must not guess replacement based on position or visual similarity.

Malformed or duplicate element IDs cause FAIL.

## 9. New PowerPoint images

For a new supported picture without `element-id`:

1. generate a new `element-id`;
2. extract the image;
3. add normalized QMD image syntax with that `element-id`;
4. add its layout to assets;
5. write the new `element-id` back to the staged PowerPoint picture shape.

## 10. Extracted/replaced image storage

Do not overwrite a shared existing source image just because one PowerPoint picture was replaced.

When PowerPoint contains image content that differs from the source represented by the current QMD path, extract it under:

```text
img/imported/<element-id>.<ext>
```

This allows separate slides/elements that previously referenced the same source image to diverge safely.

If the picture content is unchanged and the existing path remains valid, keep the existing source path where practical.

## 11. Image move and resize

For every supported image element, import reads PowerPoint shape geometry and writes:

- x
- y
- width
- height

to `<stem>.assets.json` as EMU integers.

The next QMD -> PPTX render must reproduce the imported rectangle.

## 12. Image crop and assets schema v2

PowerPoint image crop is a supported M3 feature.

M3 upgrades persistent assets to:

```json
{
  "schemaVersion": 2,
  "documentId": "document-...",
  "slideSize": {
    "width": 12192000,
    "height": 6858000,
    "unit": "emu"
  },
  "elements": [
    {
      "slideId": "slide-...",
      "elementId": "element-...",
      "type": "image",
      "path": "img/profile.png",
      "x": 1000000,
      "y": 1000000,
      "width": 3000000,
      "height": 2000000,
      "crop": {
        "unit": "ooxml-percent",
        "left": 10000,
        "top": 5000,
        "right": 15000,
        "bottom": 0
      }
    }
  ]
}
```

Crop values use the raw DrawingML/OOXML relative-rectangle percentage representation as integers, where `100000` represents 100%. This avoids unnecessary float roundoff.

Rules:

- schema v1 is accepted and interpreted as no crop.
- First write that needs M3 state migrates the file to schema v2.
- `crop` is optional; absent means no crop.
- Negative crop values emitted by PowerPoint/Open XML are preserved if structurally valid rather than clamped merely because they are negative.
- Validation requires integer values and a positive effective source rectangle: `left + right < 100000` and `top + bottom < 100000`.
- Grossly out-of-range/non-integer values or a non-positive effective source rectangle are invalid and cause FAIL; do not silently drop crop.
- The original image file is not destructively cropped solely to represent PowerPoint crop.
- QMD -> PPTX render must understand schema v1 and v2 and reapply v2 crop so a subsequent render does not lose the visible crop.
- Rotation and z-order remain out of scope.

Implementation tests must include v1 read compatibility, v1->v2 migration, zero crop, positive crop, PowerPoint-valid negative crop, invalid crop rejection, and PPTX -> assets -> PPTX crop roundtrip.

## 13. Image deletion

If an identified image is absent from a successfully parsed supported PowerPoint slide, remove that image from rebuilt QMD and assets.

Do not perform destructive cleanup until the complete import has passed validation.

## 14. Slide reorder and deletion

PPTX slide order becomes normal-slide order in rebuilt QMD after excluding the reserved front-matter title slide.

A previously managed normal slide that is no longer in the PPTX is removed from the rebuilt slide body.

Because the presentation-level marker is independent of slide IDs, deleting every previously managed normal slide does not make the presentation unmanaged. Remaining supported new normal slides can receive fresh IDs.

## 15. Unsupported content is not silently discarded

An import must not report success if the subsequent QMD -> PPTX render would silently erase unsupported user-created PowerPoint content.

Default policy:

- unsupported content with a meaningful risk of data loss -> FAIL import before commit;
- only content positively classified by the structural rules in section 7 may be ignored;
- unknown content is never classified as harmless by guesswork.

## 16. Recoverable multi-file transaction and exclusion

A multi-file filesystem update cannot be truly atomic across QMD, assets, extracted images, and PPTX. M3 therefore promises **recoverable transactional consistency**.

### Per-document exclusion and bootstrap lock

Render/import/recovery for one managed document must not run concurrently.

#### Bootstrap lock before document-id exists

A legacy schema v1 project has no `documentId` yet, so the first M3-capable render cannot derive a document-id lock safely.

Before reading/upgrading schema v1 assets or generating the first document-id, acquire a **bootstrap lock** derived only from the canonical same-stem project path:

```text
.md-slide-tool/locks/bootstrap/<sha256(canonical-paired-qmd-path)>/
```

Canonical paired QMD path means the absolute normalized path to the same-stem QMD after resolving `.` / `..` and platform path normalization appropriate to the runtime. The bootstrap key must not depend on a newly generated UUID.

Bootstrap rules:

- every M3-capable render/import entrypoint resolves the same paired QMD path before any schema migration or document-id generation;
- schema v1 / missing-documentId state acquires the bootstrap lock first;
- while holding the bootstrap lock, re-read assets/PPTX metadata because another completed process may already have migrated the project;
- if `documentId` is still absent, generate exactly one document-id, stage/write assets v2 and PPTX managed metadata under the same transaction;
- after migration completes, release the bootstrap lock;
- later commands use the normal document-id lock;
- if migration is already complete after the re-read, do not generate another ID; switch to the existing document-id lock according to the lock-order rule below.

#### Normal document lock

For an already managed schema v2 document, use:

```text
.md-slide-tool/locks/document/<document-id>/
```

#### Lock ordering

To avoid races during the transition:

1. bootstrap state: acquire bootstrap lock;
2. re-read pairing metadata;
3. if still unmigrated, complete migration while bootstrap lock remains held;
4. if migrated state is discovered, acquire the document lock before releasing bootstrap lock, then continue under document lock;
5. never acquire bootstrap after already holding the document lock.

This guarantees two concurrent first M3 renders for one schema v1 project serialize on the same bootstrap key and cannot generate competing document IDs.

General rules:

- if the required lock is already held by another live md-slide-tool process, fail with `DOCUMENT_BUSY`;
- the lock records owner/process metadata for diagnostics, but correctness relies on atomic lock acquisition rather than timestamps;
- recovery is attempted only after exclusive ownership of the relevant lock is obtained;
- implementation must use a platform/runtime locking primitive whose ownership is released on process termination, or an equivalent tested mechanism. A timestamp-only stale-lock heuristic is not acceptable.

### Transaction directory

```text
.md-slide-tool/transactions/<document-id>/<transaction-id>/
  manifest.json
  old/
  new/
```

Each manifest target records:

- final target path;
- whether the target existed before the transaction;
- old hash when it existed;
- new hash when the committed state contains a file;
- operation: create / replace / delete.

### State machine

```text
prepared -> committing -> committed -> cleanup
                  \
                   -> rolling_back -> rolled_back -> cleanup
```

Before replacing any target:

1. parse and validate the entire import;
2. stage every new output;
3. back up every pre-existing target that may be replaced/deleted;
4. record all create/replace/delete operations and hashes;
5. fsync/flush the manifest as required by the chosen runtime;
6. mark the transaction `prepared`.

Commit:

1. mark `committing`;
2. perform target operations one at a time with per-file atomic replace where supported;
3. record durable progress sufficient for failure injection/recovery;
4. verify every final target matches its expected committed state;
5. mark `committed`;
6. cleanup transaction data.

### Rollback semantics

For each operation:

- replace: if current == new, restore backed-up old; if current == old, leave it;
- delete: if target is absent, restore backed-up old; if current == old, leave it;
- create: if current == new, delete the newly created file; if target is absent, leave it.

If any current target matches neither its recorded old nor new state, automatic rollback stops with a manual-recovery error and preserves backups.

Handled commit-time failures transition to `rolling_back`, restore the pre-transaction state, mark `rolled_back`, then cleanup.

### Crash recovery

After acquiring the document lock, any later render/import checks for an existing transaction before touching presentation files.

Recovery policy is phase-specific:

- `prepared`: no target mutations are expected; verify old states, then discard staged transaction data.
- `committing` or `rolling_back`: roll back to the pre-transaction state using the operation rules above.
- `committed`: **do not roll back**. Verify every target matches the recorded new committed state and finish cleanup.
- `rolled_back`: verify pre-transaction state and finish cleanup.
- unknown/corrupt phase: stop with manual-recovery error.

This distinction ensures a crash after all replacements and after the durable `committed` record does not undo a successful import merely because cleanup was interrupted.

Failure-injection tests must cover:

- create/replace/delete rollback;
- failure after each individual target operation;
- crash before `committing`;
- crash during `committing`;
- crash after all target replacements but before `committed`;
- crash after durable `committed` but before transaction cleanup;
- concurrent second render/import receiving `DOCUMENT_BUSY`;
- recovery refusing to overwrite an unknown post-crash file state.

## 17. Text is not persisted in intermediate JSON

Continue the existing design principle:

- QMD is the persisted textual representation.
- assets stores visual element layout/state.
- presentation custom properties store only identity/version/baseline metadata.
- do not create a persistent intermediate JSON copy of slide title/body text.

Temporary transaction files are recovery mechanics, not a second canonical document store.

## CLI behavior

Initial supported form:

```bash
slidegen import presentation.pptx
```

Expected paired files:

```text
presentation.pptx
presentation.qmd
presentation.assets.json
img/
```

An M3-capable `slidegen render` also writes/refreshes the managed marker, title-slide role marker, document-id, and QMD-body baseline hash.

Do not add `--watch`, `--sync`, force-merge behavior, automatic save monitoring, or conflict merge behavior in M3.

## M3 scope

M3 includes:

- manual `slidegen import`;
- managed presentation marker/version/document-id;
- QMD render-baseline hash guard;
- reserved title-slide role marker;
- existing stable slide/element identity;
- new stable IDs for newly added supported PowerPoint slides/images;
- writing new IDs back to PPTX;
- slide title import;
- ordinary paragraph import;
- bullet/numbered-list import;
- slide reorder/delete;
- image add/delete/replace;
- image extraction under `img/imported/`;
- image x/y/width/height import;
- assets schema v2;
- image crop import and render roundtrip;
- front matter preservation;
- explicit unsupported-content detection;
- recoverable multi-file transaction and crash recovery.

## Out of scope

- arbitrary external PPTX conversion;
- heuristic import of legacy unmarked M2 PPTX (re-render once with M3-capable version instead);
- automatic watcher/sync;
- full dirty-state conflict handling/merge UX;
- automatic text merge;
- force import over a changed QMD body;
- PowerPoint Add-in;
- arbitrary shapes;
- lines/arrows;
- SmartArt;
- charts;
- arbitrary free-position text boxes;
- tables/equations unless separately approved before implementation;
- rotation;
- z-order;
- Marketplace publication;
- PPTX -> Word;
- importing PowerPoint edits to the front-matter-managed title slide.

## Future considerations

These are intentionally not M3 requirements but remain tracked:

- hide/internalize `slide-id` / `element-id` so normal users do not need to see implementation metadata;
- incremental/selective build to avoid expensive full rebuilds;
- explicit build state UI;
- prevent or safely queue edits/build requests while a build is running;
- M4 watcher/debounce/running/pending/self-generated-write suppression;
- M5 richer dirty-state conflict handling;
- shape/line/arrow support using the existing general `element-id` identity model.
